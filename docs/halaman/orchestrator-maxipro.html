      Orchestrator hanya mengoordinasi, tidak mengerjakan

      Orchestrator Utama dan Orchestrator Divisi memecah pekerjaan, memilih agen, melacak status, dan menggabungkan hasil. Pekerjaan teknis selalu dikerjakan Agen Spesialis.

      Orchestrator juga jadi teman diskusi saat sebuah lapisan terlalu berat (bloated). Orchestrator Utama bisa memecah divisi, dan Orchestrator Divisi bisa memecah agen. Keputusan diambil antar-orchestrator sendiri, lalu Pemilik menerima laporan berisi hasil dan alasannya.

      Tanda bloated (pemicu diskusi, bukan otomatis)

      • Instruksi agen lebih dari ±2.000 kata
      • Satu agen menangani lebih dari ±5 jenis tugas
      • Tingkat gagal atau revisi terus naik

      Enam hal yang wajib menunggu persetujuan Pemilik

      1. Deploy ke production
      2. Perubahan skema database production
      3. Menulis ke Odoo production
      4. Merge kode ke branch utama (kecuali perubahan yang hanya menyentuh folder agents/)
      5. Melanjutkan Tugas yang melewati batas biaya ±US$10
      6. Keputusan arsitektur besar: layanan baru, ganti teknologi database, atau mengubah kontrak API bersama

      Perubahan konfigurasi server production dianggap deploy production. Pengecualian: kalau ada error parah setelah deploy, agen 11 boleh langsung rollback ke versi sebelumnya, lalu segera melapor.

      Selain itu, semua berjalan otomatis. Sistem tidak pernah menyetujui sendiri. Kalau belum dijawab, Delegator mengingatkan setelah 24 jam dan 72 jam.

      Di dalam Software Factory

      • Setiap Tugas dimulai dari 01 Triage: menentukan Proyek, mengklasifikasi (bug, fitur, revisi, data, insiden), memberi prioritas P0–P3, menulis Kriteria Penerimaan (ukuran "hasil sudah sesuai"), menandai perubahan sensitif, dan mengusulkan Sub-tugas.
      • Orchestrator Divisi memilih agen yang dibutuhkan secara dinamis, tidak lewat pipeline tetap.
      • 09 QA selalu dijalankan sebelum merge. 10 Security wajib untuk perubahan yang menyentuh autentikasi, data pelanggan, atau kredensial.
      • Hasil yang tidak cocok dikembalikan dengan umpan balik, maksimal 2 kali ulang. Kalau masih gagal, Tugas berstatus gagal dan dilaporkan.
      • Code review di v1 = QA PASS + Security (bila perlu) + persetujuan merge Pemilik.
      • Sebelum bekerja, setiap agen wajib membaca aturan Proyek (CLAUDE.md, AGENTS.md).

      Antrean dan pekerjaan

      • Dalam satu divisi, Tugas dikerjakan satu per satu. Antar-divisi berjalan paralel. Tugas P0 menjeda Tugas yang sedang berjalan, sedangkan P1 jadi antrean pertama.
      • Setiap Tugas punya branch sendiri di repo proyek (tugas/<id>-<ringkas>), dan hasilnya berupa Pull Request.
      • Staging = staging lokal di Docker dengan database test, tanpa kredensial production WhatsApp, Telegram, atau Xendit. Odoo hanya dibaca. Deploy ke staging otomatis, deploy ke production butuh persetujuan.
      • Hanya Pemilik yang memberi Perintah, lewat Delegator. Agen tidak pernah menghubungi Pemilik langsung. Monitoring mengirim laporan insiden, tidak membuat Tugas sendiri.
      • Perintah untuk bidang yang belum punya divisi disimpan dulu sebagai Tugas berstatus diterima. Divisi baru dirancang Orchestrator Utama atas perintah Pemilik.

      Delegator dan Orchestrator Utama hanya bertukar empat jenis pesan

      PesanArahIsi

      Laporan dikirim dalam Bahasa Indonesia, hanya saat status Tugas berubah, saat ada agen baru, atau saat Tugas gagal. Detail tiap langkah bisa ditanyakan ke Delegator.

      Teknis v1

      • Claude Agent SDK di Node.js, satu proses. Orchestrator memanggil divisi dan agen sebagai subagent.
      • Status Tugas (termasuk prioritas P0–P3) disimpan di PostgreSQL, dengan tabel tugas, sub_tugas, permintaan_persetujuan, laporan, dan pertanyaan_klarifikasi.
      • v1 berjalan di komputer lokal Pemilik, dikemas dalam satu docker-compose.yml (orchestrator, PostgreSQL, database test sekali-pakai, bot Telegram). Bisa dipindah ke Mac lain yang menyala 24/7 atau ke VPS dengan langkah yang sama: clone repo, salin .env, restore database, docker compose up.
      • Selama di lokal, agen bekerja selama komputer menyala. Tugas yang terputus dilanjutkan otomatis.
      • Kartu agen disimpan di folder agents/ sendiri, lalu dibaca program dan diteruskan ke Claude Agent SDK.
      • Orchestrator memakai model yang lebih kuat. Agen Spesialis memakai model yang lebih hemat, kecuali 03 Architecture.
      • Rahasia disimpan di environment variable server, tidak pernah di repo, laporan, atau catatan.
      • Batas biaya per Tugas: lunak ±US$2 (dilaporkan), keras ±US$10 (berhenti, minta persetujuan).
      • Setiap Tugas mulai dengan konteks bersih, ditambah Catatan Divisi yang menyimpan pelajaran jangka panjang.
